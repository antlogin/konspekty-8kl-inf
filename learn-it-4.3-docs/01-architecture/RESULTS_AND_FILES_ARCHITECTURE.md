# Архитектура файлов, результатов и событий

**Версия пакета:** Learn-it 4.3  
**Статус:** рабочая архитектура; серверный event log реализован

## 1. Разделение сущностей

Нужно различать:

1. файл, который тренажёр создаёт для ученика;
2. данные о прохождении попытки;
3. опубликованный HTML самого тренажёра.

Они имеют разные жизненные циклы и не должны передаваться одним механизмом.

## 2. Файлы ученика

Базовая схема:

```text
тренажёр → формирует файл → браузер сохраняет файл локально
```

Тип файла определяется заданием: `.txt`, `.json`, исходный код, изображение и т. п.

В базовой архитектуре файл:

- не хранится в Git и в бакетах сайтов;
- не отправляется через Netlify Forms (они выведены из использования).

Если учитель должен получить результат, страница дополнительно отправляет копию через событие `result_submitted` (раздел 2a). Локальное сохранение при этом остаётся: это запасной канал, если сеть недоступна.

Централизованный upload произвольных файлов, если он потребуется, должен иметь отдельный API, объектное хранилище, аутентификацию и политику хранения.

## 2a. Результат для учителя: `result_submitted`

```text
страница → CloudForm (как FormData) → cloudSubmit → POST /api/v1/events
```

- отправляется одно событие `result_submitted` с полями формы и файлами;
- ZIP с одним несжатым JSON распаковывается на клиенте и сохраняется в YDB как читаемый JSON;
- иной файл передаётся в base64;
- `attemptId` = `form-<session_id>`, `trainerId` = `<имя формы>:<trainer_id или lesson>`;
- успехом считается только ответ `200` с `{"ok": true}`; при ошибке ученик видит сообщение и сохраняет файл локально.

Это не замена upload-подсистемы: крупные файлы так отправлять нельзя. Формат — [TRAINER_TELEMETRY_SPEC.md](../05-telemetry/TRAINER_TELEMETRY_SPEC.md), раздел 30.

## 3. Результат прохождения

Результат рассматривается как попытка (`attempt`) и упорядоченный поток событий:

```text
attempt_started
      ↓
seq=2
      ↓
seq=3
      ↓
...
      ↓
attempt_finished
```

Один запуск создаёт один новый `attemptId`. `seq` начинается с 1 и монотонно возрастает внутри попытки.

## 4. Почему хранится event log

Один итоговый балл не позволяет восстановить процесс работы. Сырые события дают возможность позднее вычислять:

- длительность;
- время до первого действия;
- последовательность изменений ответа;
- повторные подтверждения страниц;
- видимость вопросов;
- уход страницы в background;
- idle-периоды;
- сетевые разрывы;
- итоговые ответы и результат.

Интерпретация поведения выполняется отдельно. Клиент не должен присваивать ученику `cheating score`, `suspicion score` или аналогичные выводы.

## 5. Факты и интерпретация

Событие `visibility_hidden` означает только то, что страница перестала быть видимой. Оно не означает использование стороннего ресурса.

События `copy`, `paste`, `cut`, `context_menu` фиксируют технический факт действия; содержимое буфера обмена не сохраняется.

Аналитика должна отделять наблюдаемое событие от педагогической интерпретации.

## 6. Идентификация

Главный идентификатор назначения — `trainerId`.

Главный идентификатор отдельного прохождения — `attemptId`.

Для ученика текущий клиент может передавать:

```text
firstName
lastName
className
studentId (если существует)
```

При группировке предпочтителен порядок:

```text
studentId
→ ФИО + класс
→ attemptId
```

Персональные данные следует собирать только в объёме, необходимом для учебной задачи.

## 7. Хранение

Текущая серверная схема содержит:

```text
events   — используется
attempts — создана, пока не заполняется рабочей функцией
```

`events.payload_json` хранит исходное событие целиком. Индексируемые поля вынесены отдельно лишь для базового доступа.

## 8. Идемпотентность

Ключ события в YDB:

```text
(attempt_id, seq)
```

Запись выполняется через `UPSERT`. Поэтому один и тот же пакет можно отправить повторно с теми же `attemptId` и `seq`: второй экземпляр строки не создаётся.

## 9. Клиентская очередь

Минимальная текущая реализация использует `pendingEvents` в памяти.

Правило неизменно:

```text
создать событие
→ добавить в очередь
→ отправить
→ получить HTTP 200 и ok=true
→ только после этого удалить из очереди
```

Если отправка не удалась, события остаются для retry.

Устойчивая очередь IndexedDB — следующий этап и нужна для сохранения неотправленных событий при закрытии вкладки/браузера.

## 10. Локальный JSON попытки

Тренажёр должен сохранять возможность выгрузить полный JSON попытки. Он используется для:

- резервной копии;
- диагностики;
- ручного импорта;
- сравнения локальной и облачной записи.

Минимальная структура включает `trainerId`, `trainerVersion`, `attemptId`, данные ученика, время начала/окончания, `summary` и `events`.

## 11. Безопасность и доступ

Клиент не имеет прямого доступа к YDB и не содержит облачных секретов.

Чтение событий (`GET /api/v1/events`) и удаление попытки (`DELETE /api/v1/attempts/{attemptId}`) доступны только с ключом учителя; публичного чтения нет. На сервере есть фильтры `trainerId`, `since`, `compact`, `limit`.

Пока не реализованы:

- пагинация;
- отдельные ключи для разных учителей.

События содержат имена и фамилии учеников, поэтому ключ учителя нельзя вставлять в публичные материалы, а просмотрщики результатов хранятся только у учителя (`LOCAL_…`).

## 12. Независимость от публикации

```text
GitHub → GitHub Actions → Yandex Object Storage → HTML
```

и

```text
HTML → Telemetry API → Yandex Cloud
```

являются разными контурами. Недоступность Yandex Cloud не должна препятствовать открытию материала.

## 13. Зафиксированный принцип

```text
ученический файл → локально (+ копия учителю через result_submitted, если предусмотрено)

процесс прохождения → ordered events → Telemetry API → YDB

аналитика → строится поверх сохранённых событий
```
